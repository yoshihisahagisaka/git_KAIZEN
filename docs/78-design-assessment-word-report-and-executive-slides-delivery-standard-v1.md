# IT経営KAIZEN — 設計Assessment Word Report + Executive Slides Delivery Standard v1

Status: **CANONICAL — BUSINESS / DELIVERABLE MODEL**
Date: 2026-09-14
Related: `docs/73-it-management-kaizen-design-assessment-standard-offer-v1.md`, `docs/77-it-management-kaizen-customer-language-and-assessment-deliverable-principles-v1.md`

## 1. Decision

設計Assessmentの正式成果物は、**Word型の詳細レポートを正本**とし、経営会議・報告会・社内共有を支援する**Executive Summaryスライドを併せて提供する**。

> **正本：IT経営KAIZEN 改善計画書（Word型レポート → PDF納品）**
>
> **要約：経営判断用 Executive Summaryスライド**
>
> **裏付け：調査・分析編 / Evidence Book**

スライドだけを正式成果物としない。

---

## 2. Why Word-first

設計Assessmentは「説明を聞けば分かる資料」ではなく、顧客が後から一人で読み返しても判断の背景を理解できる成果物を目指す。

箇条書き中心のスライドは視認性が高い一方、以下が省略されやすい。

- なぜその事実が重要なのか
- 目指す姿とどう関係するのか
- なぜその原因と考えるのか
- なぜその改善案につながるのか
- 各選択肢の違いは何か
- なぜその進め方を推奨するのか
- 何が未確認なのか

その結果、コンサルタントまたは営業担当者による口頭補足がないと意味が伝わらない成果物になり得る。

Word型レポートでは、図表と文章解説を組み合わせ、判断の論理を成果物自体に残す。

---

## 3. Read-to-Understand Principle

顧客向け成果物の品質基準として以下を採用する。

> **説明を受けなければ分からない資料にしない。**

> **経営者が後から一人で読み返しても、「何が事実で、なぜ重要で、どんな選択肢があり、なぜこの提案なのか」を理解できる成果物にする。**

ただし、文章量を増やすこと自体を価値としない。文章は「判断に必要な意味・因果・前提」を説明するために使う。

---

## 4. Three-layer Deliverable

### Layer A — 経営判断編
Word型レポートの本編。経営者が読んで理解・比較・判断できる内容とする。

### Layer B — 調査・分析編
確認資料、事実、分析、未確認事項、業務・システム・費用・管理状況等を示し、本編の判断根拠を追跡可能にする。

### Layer C — Executive Summary Slides
経営会議、報告会、役員説明等で短時間に全体像と判断事項を共有するための要約版。

スライドはWordレポートと別の結論を作らない。正本を圧縮・可視化したものとする。

---

## 5. 経営判断編 — Writing Standard

各主要Sectionは、箇条書きだけで完結させず、原則として次の組合せを使う。

1. **結論 / 見出し** — このページ・節で何を伝えるか
2. **解説本文** — なぜ重要か、何を確認したか、どう解釈するか
3. **図表** — 構造・比較・時間軸・関係性を視覚化
4. **判断の根拠** — どの事実・確認資料に基づくか
5. **経営への意味** — 会社の目指す姿や投資判断とどう関係するか
6. **未確認事項 / 注意点** — 分からないことを隠さない

例：

### 見出し
入社対応は、社員数の増加に比例してIT担当者の作業が増える構造です。

### 解説
現在、入社時のアカウント作成、各業務システムへの登録、PC設定は、それぞれ個別の手順としてIT担当者が実施しています。個々の作業自体に問題があるわけではありませんが、今後社員数が増えた場合、入社人数に比例してIT担当者の作業も増える構造になっています。

今回確認した範囲では、これらを一連の「入社対応」として管理し、自動化・標準化する仕組みは確認できませんでした。

### 経営への意味
「社員数が増えてもIT管理人員を大幅に増やさない」という目指す姿に対し、現在の運用方法にはギャップがあります。

このように、事実の列挙だけでなく「だから経営上どういう意味があるか」まで文章で説明する。

---

## 6. 経営判断編 — Proposed Chapter Structure

ページ数は固定しない。初期標準案として以下を採用し、Pilotで検証する。

1. はじめに — 今回のAssessmentの目的と判断テーマ
2. エグゼクティブサマリー
3. 実現したい会社の姿
4. 今回確認した範囲と確認方法
5. 現在のIT環境・運用の全体像
6. 確認できた重要な事実
7. まだ確認できていないこと
8. 目指す姿とのギャップ
9. なぜ現在の状態になっているのか
10. 事実から改善案へ至るつながり
11. 改善の選択肢
12. 経営として選べる改善プラン
13. 改善プランA — 複数年改善計画 / 投資 / 期待する変化 / 注意点
14. 改善プランB — 複数年改善計画 / 投資 / 期待する変化 / 注意点
15. 必要な場合、改善プランC以降
16. 改善プラン比較
17. atLIBからの提案と、その根拠
18. 経営者に判断いただきたいこと
19. 選択した改善計画
20. 実行後に確認すること
21. 次回の経営判断時期

---

## 7. 調査・分析編

調査・分析編は本編の「裏側」ではあるが、単なる資料置き場にしない。

主要な判断がどの確認資料・事実に基づくか追跡できるよう整理する。

案件に応じて以下を含む。

- 確認資料一覧と出所
- ヒアリング対象 / 確認内容
- システム構成
- アカウント / 認証
- PC / Device / Asset
- SaaS / License / Contract
- Network / Infrastructure
- Security
- 業務Flow / 手順
- 問い合わせ / Request
- 工数 / Workload Baseline
- IT Cost / Vendor Cost
- 組織 / Responsibility / Authority
- Rule / Governance / Risk
- 事実 / 未確認事項 / 仮説
- 各改善案の根拠

本編から調査・分析編の該当箇所を参照できる構造を目指す。

---

## 8. Executive Summary Slides

スライドの役割は「詳細説明の代替」ではなく「経営会議での判断支援」とする。

想定構成：

1. 実現したい会社の姿
2. 現在地 — 重要な事実とギャップ
3. なぜ起きているのか
4. 改善の選択肢
5. 改善プラン比較
6. 改善プランAの複数年計画
7. 改善プランBの複数年計画
8. 必要なら改善プランC
9. atLIBからの提案と根拠
10. 今回判断いただきたいこと
11. 選択後の進め方 / 効果確認

枚数は固定しない。

スライドだけを見ても大筋を理解できるようにするが、詳細な根拠はWordレポートを正とする。

---

## 9. Scenario / Roadmap Rule

複数の改善プランを提示する場合、それぞれに対応する複数年改善計画を提示する。

```text
改善プランA
→ 改善計画A
→ 年度別投資A
→ 期待する変化A
→ 注意点A

改善プランB
→ 改善計画B
→ 年度別投資B
→ 期待する変化B
→ 注意点B
```

比較ページでは、各プランについて少なくとも以下を比較する。

- 何を優先するプランか
- 1年目に何をするか
- 2年目以降の方向
- 投資の特徴
- 期待する変化
- 注意点 / Risk
- どのような会社に向くか
- 判断に残る未確認事項

---

## 10. Language Standard

Customer-facingでは日本語を第一とする。

内部用語をそのまま大量に表示しない。

- FUTURE → 実現したい会社の姿
- FACT → 確認できた事実
- UNKNOWN → まだ確認できていないこと
- GAP → 目指す姿とのギャップ
- ROOT CAUSE → なぜ起きているのか / 根本原因
- ACT Options → 改善の選択肢
- Scenario → 改善プラン
- Roadmap → 改善計画
- Expected CHANGE → 期待する変化
- Evidence → 判断の根拠 / 確認資料

詳細はdoc77を正とする。

---

## 11. Format Principle

Word型レポートだから文章だけにしない。

以下を積極的に使用する。

- 図解
- Before / After
- 業務Flow
- システム構成図
- 比較表
- 因果図
- 年度別改善計画
- 投資推移
- 判断の分岐
- 確認資料への参照

> **文章で意味を説明し、図表で構造を理解させる。**

---

## 12. Delivery Format

標準Delivery Proposal：

- 編集可能なWord原本：必要に応じて社内保管
- Customer納品正本：PDF
- Executive Summary：PowerPoint / PDF
- 調査・分析編：Word/PDFまたは適切な表形式

実際のファイル形式・編集可能原本のCustomer提供範囲はCommercial / Operational Ruleとして別途決定できる。

---

## 13. Validation

Pilotで以下を確認する。

- 経営者が口頭説明なしでも主要な結論を理解できるか
- なぜその改善案なのかをレポートだけで追えるか
- Word本編の文章量は多すぎないか / 少なすぎないか
- 図表と本文のバランス
- Executive Summaryだけでも経営会議で議論できるか
- 詳細質問時にWord / 調査・分析編へ戻れるか
- 120万円の成果物として十分なDecision Valueを感じるか
- 作成工数が標準価格内で成立するか

---

## 14. Supersession / Interpretation

既存文書でCustomer-facing成果物をスライド中心に読める記述がある場合、本Canonicalを優先する。

設計Assessmentの正式成果物モデルは、**Word型詳細レポートを正本 + Executive Summaryスライド + 調査・分析編**とする。
