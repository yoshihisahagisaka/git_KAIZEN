# 無料 IT経営診断 チャネル別業務フロー v1.0

Status: **CANONICAL — SERVICE OPERATION / CHANNEL FLOW**

この文書は、無料 IT経営診断の標準導線と営業訪問時の代替導線を分けて記録する。

## 1. 基本方針

無料 IT経営診断の**原則導線はWeb**とする。

> **Web導線を標準とし、営業訪問導線は同じ診断データモデルを使う別チャネルとして設計する。**

両者を混同しない。ただし、診断ロジック・データ構造・FACT FIRSTの原則は共通化する。

## 2. 標準導線 — Web

### Flow

> **LP / Web申込 → 事前アンケート → AI事前整理 → 担当者レビュー → 60分診断 → ヒアリング内容整理 → 人間確認 → 無料診断レポート生成 → 経営フィードバック → IT経営KAIZEN 設計Assessment提案**

### 2.1 LP / Web申込

顧客が無料 IT経営診断へ申し込む。

会社基本情報、連絡先等は可能な限り申込情報として取得し、診断質問数を増やさない。

### 2.2 事前アンケート

目標回答時間：**3〜5分**。

Future Firstで、現在のCanonicalで定義した9問＋任意自由記述を基本とする。

目的は診断結果を確定することではなく、Futureと重点確認領域を把握すること。

### 2.3 AI事前整理

AIは事前回答から、60分診断で確認すべき重点テーマを原則3〜5件提案する。

出力例：

- Futureとの関係
- 回答内容
- 現時点で分かっていること
- UNKNOWN
- Hypothesis
- 推奨ヒアリング質問
- AssessmentでEvidence確認候補となり得る事項

AIは診断結果を確定しない。

### 2.4 担当者レビュー

担当者がAI提案を確認し、採用・削除・追加・順序変更を行う。

> **AI Suggests. Human Decides.**

### 2.5 60分診断

冒頭でFutureを再確認し、重点テーマを中心にヒアリングする。

固定質問をすべて消化することを目的としない。途中で重要な新情報が出た場合は、必要に応じて深掘り対象を変更する。

### 2.6 ヒアリング内容整理

AIはヒアリング内容を以下の意味状態へ整理する。

- 回答・発言
- Observation
- 現時点で確認できた内容
- UNKNOWN
- Hypothesis
- Gapの可能性
- AssessmentでEvidence確認した方がよい事項

顧客発言だけで企業実態を確定FACTへ昇格させない。

### 2.7 人間確認

担当者がAI整理内容を確認・修正・承認する。

人間確認後に無料診断レポートを生成する。

### 2.8 無料診断レポート生成

レポートは、ヒアリング内容から「可能性」を提示する。

基本構造：

> **Future → ヒアリングから見えていること → 現時点で分からないこと → Gapの可能性 → Root Cause仮説 / KAIZENの方向性 → 次に確認・判断すべきこと**

Evidence未確認の内容を断定しない。

### 2.9 経営フィードバック

レポートを送付するだけで終えず、担当者が経営者へ説明する。

説明の中心：

> **今回見えているのは可能性であり、ここから先はEvidenceを確認しないと実態を断定できない。**

### 2.10 Assessment提案

> **可能性で会社を変えない。事実を確認してから、何を変えるかを決める。**

として、**IT経営KAIZEN 設計Assessment（80万円・税別）**へ接続する。

## 3. 別チャネル — 営業訪問

営業訪問では、顧客にWeb事前アンケートを事前入力してもらえないケースを想定する。

### Flow

> **営業訪問 → 営業担当者がヒアリングし代理入力 → 必要箇所のみ追加確認 → AI即時整理 / 重点テーマ提案 → 担当者が確認 → 60分診断へ移行または別日設定 → ヒアリング内容整理 → 人間確認 → 無料診断レポート → 経営フィードバック → Assessment提案**

### 3.1 営業訪問時の初期ヒアリング

目安：**10〜15分**。

営業担当者は、Web事前アンケートと同じ基本データモデルを使って代理入力する。

Future Firstを維持する。

### 3.2 追加確認

営業画面には、必要な項目だけ深掘りできる「追加確認」を設ける。

例：

Q8「IT情報が経営判断に使える形で届いているか」に対して、

- そもそもIT情報が管理されていない
- 担当者では管理されている
- 経営への報告がない
- 報告はあるが意味が伝わらない
- 判断に必要な情報が不足している
- 現時点ではまだ判断できない

等を必要な場合だけ追加確認する。

### 3.3 営業訪問での重要ルール

営業担当者が聞いた内容を、そのままFACTへしない。

営業担当者自身の解釈も、顧客発言とは分離する。

保持すべき意味状態：

- 顧客発言
- 営業担当者のObservation
- Hypothesis
- UNKNOWN
- 確認済みEvidence（存在する場合のみ）
- 要追加確認

### 3.4 60分診断への接続

営業訪問だけで十分な確認時間を取れない場合は、その場で診断を完結させない。

初期ヒアリング結果をもとにAIが重点テーマを整理し、別途60分診断を設定する。

営業訪問時に十分な時間が確保され、適切な担当者が対応できる場合は、そのまま60分診断相当の深掘りへ進んでもよい。

ただし、診断品質を営業担当者個人のスキルだけに依存させない。

## 4. Web導線と営業訪問導線の共通部分

共通化するもの：

- Future First
- 基本質問データモデル
- 重点テーマ生成ロジック
- FACT / UNKNOWN / Observation / Hypothesis の意味分離
- 60分診断の深掘りロジック
- AI提案 → 人間確認
- 無料診断レポート
- 経営フィードバック
- Assessmentへの価値境界

チャネルごとに別の診断思想を作らない。

## 5. 相違点

| 項目 | Web導線 | 営業訪問導線 |
|---|---|---|
| 位置づけ | **標準導線** | 別チャネル |
| 初回入力者 | 顧客 | 営業担当者が代理入力 |
| 初回所要時間 | 3〜5分 | 10〜15分目安 |
| 深掘り | 原則60分診断で実施 | 訪問中に必要箇所を一部追加確認可能 |
| AI事前整理 | 60分診断前 | 初期ヒアリング後に即時整理可能 |
| 目的 | 自然流入・再現性・スケール | 営業接点を診断入口へ変換 |

## 6. サービス運用上の原則

> **Web First. Same Method. Different Entry.**

日本語では：

> **標準はWeb。入口が違っても、診断方法は同じ。**

営業訪問を理由に、FACT FIRST、Future First、人間確認、Evidence未確認事項を断定しないという原則を弱めない。

## 7. 今後のシステム要件への反映

診断システムでは、少なくとも以下を区別する。

- `entry_channel = web`
- `entry_channel = sales_visit`

ただし、以後の診断データモデルは極力共通化する。

営業訪問専用画面では、代理入力、追加確認、メモ、Observation/Hypothesis分離を支援する。

Web顧客画面では、回答負荷を下げ、3〜5分で完了することを優先する。
