Base #139 / 263dbce. Accepted scope in sonix-p0a-teams-notification-decision-20261126.md; Product Operating Principles 1,5,7,8,9,15 and Decision 5/6 retained.

- Fit: Service/Contract and Actor session/grant kernel, parent SUPPORT Work optional, existing append-only lifecycle and Teams transport. Existing escalation is explicit specialist request only; cannot model partner-originated generic request without parent Work or narrow publication boundary. Current SUPPORT grant kinds are SUPPORT/REGISTRY/PROCEDURE/KNOWLEDGE, scopes SERVICE/RECIPIENT/WORK. No independent request-scoped authority. Do not expose full Work or infer access from mention roster.
- Gap: generic exchange requires durable request record and append-only response/update projection, standalone or optional parent Work. Proposed application-level persistence (not new Core Work type): request publication plus revision events; no duplicate status authority. Sender/recipient parties resolved from service configuration, explicit participant access separate from SUPPORT. No fixed workflow engine.
- This slice adds pure shared category validation and status/revision/response contract. Direction labels are generic provider/partner; onsite allowed provider-to-partner only for configured initial service. Completion requires result, direct completion allowed; repeat status with comment permitted. Reopen after completion blocked pending explicit correction/reopen design (not destructive overwrite). Optional customer/contact/due fields provisional UI defaults. No API, database, authorization or real notification enabled in this slice.
- Next gate: design explicit party/actor bindings using existing verified identity and scoped grant management; tenant/service/contract and publication scope checked before listing/detail/update, sender read only, recipient update only; current grant recheck and locking. Use minimal append-only request storage and durable notification intents after authority Fit/Gap. No real customer identifiers in Git, no production Go.

## PWA basic support — user-approved 2026-11-26
Include installable mobile web portal in initial release. Use generic service-configured portal branding (SONIX ONE for initial service), manifest, app icons, standalone display, mobile-responsive request form/list/detail and authenticated deep links from Teams. Android Chrome and iOS Safari home-screen installation must be verified on actual devices. Teams remains the notification channel; Web Push, OS badge count, native app distribution and offline submission are excluded. Do not cache authenticated HTML/API responses, personal data or credentials in a service worker; static public assets only if caching is needed. Session expiry and authorization apply equally to installed and browser modes. Teams links may open a browser rather than the installed app depending on OS; require successful authenticated navigation, not forced app launch. No new Core object or SONIX-only application. Implementation and device acceptance pending. No production changes.

## Web Push and app badge — user-approved extension 2026-11-26
This supersedes the preceding PWA baseline exclusions for Web Push and OS badge only. Initial release includes generic FACTACT Web Push notification support, using the same authorized request event and per-Actor unread projection as in-app notification; retain Teams delivery independently. No native app or offline submission. Service configuration controls enabled notification channels, and each authenticated user explicitly opts in on each device. Use standard Web Push, VAPID secrets in deployment secret management, service worker push/notificationclick handlers and device subscription lifecycle. Bind subscriptions to verified tenant/Actor, enforce current request READ authority and active session/account policy before dispatch, isolate tenants, revoke on logout/account switch or invalid subscriptions, and never infer permission from mention roster. Store no customer data in payload/lock-screen notification; use generic text and authorized same-origin request deep link. No authenticated HTML/API response cache. Keep notification attempts and business request state separate; retry only safe delivery failures, handle expired subscriptions and avoid duplicate notifications for the same event/device. Use feature detection for badges: iOS installed web app Badging API where available, Android launcher notification dot/badge dependent on OS/launcher settings, no guaranteed numeric badge. In-app unread count is authoritative and updates on opening/acknowledgement; OS badge is best effort. Real Android Chrome and iOS home-screen PWA acceptance: permission granted/denied, foreground/background/closed, notification tap/login, read acknowledgement, badge clearing where supported, multiple devices, logout/revocation and no cross-tenant disclosure. No production activation or real push before acceptance/Go. Implementation pending; use existing request notification projection and minimal channel-specific transport, not a generalized workflow engine.
