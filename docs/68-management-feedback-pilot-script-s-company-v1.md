# IT経営KAIZEN — S社 Management Feedback Pilot Script v1

Status: BUSINESS / PILOT EXECUTION — PROPOSAL FOR VALIDATION
Date: 2026-09-14

## 0. Purpose

無料IT経営診断後のManagement Feedbackを、実顧客S社をモデルとして45分で実行できるレベルまで具体化する。

この場の目的はAssessmentを販売することではない。

> FUTUREに対して、今どこまで分かっていて、何がまだ分からず、次に何をDecisionする必要があるかを経営者と共有する。

---

# 1. S社 — Pre-Feedback FACT / UNKNOWN

## Customer FACT — user-provided

- 従業員規模：200〜300名
- IPO準備中
- 情報システム部長が先月退職
- 新任の課長候補が着任予定 / 着任する
- 情報システム部は情報システム課となり、取締役本部長の所掌となる
- 取締役本部長は人事部等も所掌している
- 取締役本部長はITの知見があまりない
- atLIBは取締役本部長と接点がある
- 現在、業務委託1名が常駐
- 常駐者の主な業務：PCキッティング、スマホキッティング、請求書管理、問い合わせ対応

## UNKNOWN — Feedback前に分かったことにしない

- IPOの具体的目標時期 / 現在の審査・準備Phase
- IPO準備においてIT統制・情報セキュリティ・ITGC等で既に指摘 / 要求されている事項
- 取締役本部長が1〜3年後に実現したい会社のFUTURE
- 新任課長の責任範囲、権限、IT Capability
- 現在のIT資産 / SaaS / Account / Security / Network / Vendor全体像
- ITに関する規程、承認、権限、Evidenceの現状
- 問い合わせ量、キッティング量、請求書管理量、Human Work
- 常駐1名以外の社内 / 外部IT Capability
- 退職した部長に依存していたDecision / Knowledge / Vendor Relation
- 今後の人員計画 / 組織変更 / 拠点 / M&A等
- 現時点の重要IT課題の優先順位

## HYPOTHESIS — Customer FACTとして扱わない

- IT責任者交代により、Decision / Knowledge / GovernanceのContinuity Gapが存在する可能性
- IPO準備に伴い、IT運用を「担当者が回している状態」から「説明可能で再現可能な状態」へ移す必要がある可能性
- 常駐者が定常業務を担う一方、経営・管理・改善Capabilityが不足している可能性
- 新任課長が日常運用に吸収されると、IPO / IT改善 / 経営課題へ時間を使えない可能性

# 2. 45-minute Management Feedback Agenda

45分はPilot candidate。実測して調整する。

## 0–5 min — Opening / Boundary

### Objective

この場を「診断結果の正解発表」や「Assessment営業会」にしない。

### Suggested Script

> 本日は、ITの問題点を断定する場ではありません。まず、今後どんな会社にしたいのかを確認し、そのFUTUREに対して、現時点で分かっていることと、まだ確認できていないことを分けます。その上で、次に何を判断する必要があるかを一緒に整理します。

### Screen / Report

- IT経営KAIZEN Methodの簡易図
- FUTURE → FACT / UNKNOWN → GAP → WHY → NEXT DECISION

---

# 3. 5–13 min — Block 1: FUTURE

## Key Question

> IPOを一つの節目としたとき、1〜3年後、ITの面でもどんな会社になっていたいですか？

## Follow-up Candidates

- 経営として、ITに何を期待していますか？
- IPO準備を終えること自体がゴールですか。それとも、その先に実現したい状態がありますか？
- 新しい情報システム課に、日常運用以外で何を担ってほしいですか？
- 社員にとってITがどうなっていると「会社が良くなった」と言えますか？
- 経営側から見て、ITについて何が見えるようになっていると判断しやすいですか？

## Capture

- Customer wordingを優先したFUTURE
- Desired State
- Business Trigger
- Management expectation

## Guardrail

「IPO対応を整える会社」を勝手にFUTUREにしない。IPOはTrigger / constraintであり得るが、FUTUREは経営者に確認する。

---

# 4. 13–21 min — Block 2: FACT / UNKNOWN

## Show — Confirmed Customer Input

現時点で把握している情報として以下を提示し、誤りをCustomerにCorrectionしてもらう。

- 200〜300名規模
- IPO準備中
- IT部長退職 → 情報システム課へ組織変更
- 取締役本部長の所掌へ
- 新任課長候補が着任
- 業務委託1名が常駐
- 常駐者はPC / スマホキッティング、請求書管理、問い合わせ対応を担当

## Show — UNKNOWN

例：

- IPOに必要なIT統制 / Evidenceの現在地
- IT責任 / 権限 / Decision構造
- 退職部長が持っていたKnowledge / Vendor Relation
- 新任課長が担うべき仕事と、任せるべき仕事
- IT資産 / SaaS / Security / Account / Vendorの全体像
- 日常運用に必要なHuman Workと改善余地

## Customer Question

> この中で、すでに分かっていること、違っていること、逆に経営として特に見えていないことはありますか？

## Output

- Corrected Customer Input
- Newly identified UNKNOWN
- Candidate Evidence Needed

---

# 5. 21–28 min — Block 3: GAP

GAPはFUTUREが確認されてから形成する。

## Candidate GAP Frame — HYPOTHESIS until FUTURE confirmed

### Governance / Management

FUTUREで必要なIT Management Capabilityに対して、責任・権限・判断材料が十分か。

### Continuity

部長退職後もKnowledge / Vendor / Decision / Evidenceが組織として継続できるか。

### Operation

新任課長が経営・改善へ時間を使えるよう、定常業務の役割分担が設計されているか。

### IPO / Trust

IPO準備で必要となるIT統制・Security・Evidenceが説明可能な状態か。

## Suggested Script

> 現時点では、ここを「問題」と断定するのではなく、FUTUREに対して確認が必要なGAP候補として見ています。

---

# 6. 28–34 min — Block 4: WHY — Hypothesis

## Candidate Root Cause Hypotheses

- IT運用とIT Managementの役割が明確に分かれていない
- Knowledge / Decision / Evidenceが人に寄っていた
- 定常業務を回すことが優先され、改善 / 経営判断の時間が確保しにくい
- IPO準備に必要なIT Capabilityと現在の体制の差がまだ可視化されていない

## Guardrail

上記は診断で確定したROOT CAUSEではない。

### Language

NG:
> 原因は○○です。

OK:
> 現時点では○○の可能性があります。判断するには△△のEvidence確認が必要です。

---

# 7. 34–42 min — Block 5: NEXT DECISION

## Management Decision Question

> FUTUREを実現するために、まず何を明らかにしてから次の投資・体制・施策を決めるべきでしょうか？

## Candidate Decision Themes

1. 新しい情報システム課に必要なIT Capabilityは何か
2. 新任課長が担うべきManagement / Improvementと、定常運用の役割分担をどうするか
3. IPO準備に対してIT統制 / Security / Evidenceのどこまでを確認する必要があるか
4. 現在のIT環境・Vendor・運用のどこを残し、整え、変えるか

## Route Decision

Human DecisionでA/B/C/Dへ。

- A Direct ACT
- B Focused Confirmation
- C 設計Assessment
- D Stop / Hold

### Route C candidate condition for S社

以下のようなDecisionを行うにはEvidence不足がMaterialである場合：

- IT組織 / 役割の再設計
- IPOを見据えたIT統制 / Security改善
- Vendor / Managed CapabilityのScope Decision
- 複数のIT施策の優先順位 / 投資Decision

### Assessment Transition

> ここから先は、可能性のまま投資や体制を決めるのではなく、必要なEvidenceを確認して現在地と次の一手を確定する必要があります。そのための工程がIT経営KAIZENの設計Assessmentです。

Assessmentを推奨するかはHumanがこの場のEvidence / UNKNOWNを見て判断する。

---

# 8. 42–45 min — Close / Customer Restatement

## Key Test

説明者ではなくCustomerに確認する。

> 今日の話を踏まえると、次に何を確認・判断する必要があると感じましたか？

## Capture

- Customer restatement
- Selected Route
- Next Action
- Actor if already decided
- Follow-up / answer timing if applicable
- Customer questions / objections

Customerが次のActionを自分の言葉で説明できない場合、Feedbackの理解が十分だったとみなさない。

# 9. Management Feedback Report / Screen Structure

Pilotでは5画面 / 5ページを基本候補とする。

## Page 1 — FUTURE

Headline:
> 1〜3年後、どんな会社にしたいか

Content:
- Customer wording
- Business Trigger
- Management expectation

## Page 2 — FACT / UNKNOWN

Two-column:
- 現時点で確認できていること
- まだ確認が必要なこと

Customer InputとEvidence-confirmed FACTをUI / wording上で混同しない。

## Page 3 — GAP

Headline:
> FUTUREとの間で、何を確認する必要があるか

- Management / Governance
- Continuity
- Operation
- IPO / Trust

Confirmed GAPとCandidate GAPを区別する。

## Page 4 — WHY

Headline:
> なぜ起きている可能性があるか

Each item:
- Hypothesis
- Supporting Observation
- Evidence Needed

断定表現を使わない。

## Page 5 — NEXT DECISION

Headline:
> 次に、何を決めるか

Show:
- Material Decision
- Evidence Needed
- Route A / B / C / D
- Next Action

AssessmentはRoute Cの場合にのみ表示 / 説明する。

# 12. Business Use Cases for Product Lane Architecture Validation

This section is Architecture Validation Input, not a Product specification change request.

## Use Case A — Management Feedback Next Decision

### Business Use Case
Management FeedbackでCustomerがNext Decision / Routeを選び、その後のActionへ継続する。

### Why
Feedbackを説明会で終わらせず、Decision → ACTへ接続するため。

### Information / Evidence
FUTURE, Customer Input, UNKNOWN, GAP, Hypothesis, Evidence Needed, Decision, rationale, selected Route, Next Action.

### Required Connection
Management Feedback → Decision → Next Action / ACT.

### Business Requirement
Decisionと、その時点で何が分かっていたか / 分からなかったかを後から追える。

### Not Required
新しいManagement Feedback Core Objectを要求しない。

## Use Case B — Follow-up semantics

### Business Use Case
Management Feedback後に、Assessment回答予定日、追加Evidence確認日、ACT期限、Verification日等を扱う。

### Why
「期限」「約束日」「確認日」「再開日」はBusiness上意味が異なる。

### Required Connection
Decision / ACT / Evidence request / Verificationと、それぞれの時間意味。

### Business Requirement
単一のDue Dateへ意味を潰さない。

### Not Required
SUPPORT専用Due semanticsを要求しない。

## Use Case C — Assessment Context Continuity

### Business Use Case
無料診断 / Feedbackで形成したContextをAssessmentへ、AssessmentでHuman ApprovedとなったContextをACT / FACTACT運用へ継続する。

### Why
同じ情報の再入力と、診断資料でKnowledgeが途切れることを防ぐ。

### Required Connection
Diagnosis → Feedback → Assessment → Decision → ACT → Verification.

### Business Requirement
ProvenanceとApproval stateを失わずにContextを継承できる。

### Not Required
Business用語をそのまま新Core Object / Tableにしない。
