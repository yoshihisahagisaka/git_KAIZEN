# IT経営KAIZEN 設計Assessment 顧客価値設計原則 v1.2

Status: **CANONICAL — BUSINESS / CUSTOMER VALUE PRINCIPLE**

この文書は、IT経営KAIZEN 設計Assessmentの商品設計における顧客価値の基準を記録する。

## 1. 商品設計の順序

Assessmentは、既存の価格に見合う作業量・成果物を逆算して設計しない。

> **IT経営KAIZENの原則・思想から顧客体験と価値を設計し、その結果として提供内容・工数・適正価格を決める。**

現在設定している80万円（税別）は価格の基準点ではあるが、サービス設計を80万円へ合わせることを目的としない。顧客体験・提供価値・実施内容を確定した後、価格は最終的に再検討する。

## 2. Assessmentの中心顧客価値

提供価値：

> **事実をもとに、IT経営の次の一手を判断する材料を提供する。**

顧客の到達状態：

> **経営者が、事実をもとにIT経営の次の一手を決められる。**

Assessmentの価値は、調査量、資料量、診断項目数、スコア、レポートの見栄えそのものではない。

経営者が、自社のFutureと現在地を事実に基づいて理解し、何を変えるか、何をやめるか、何を残すか、何を任せるか、何に投資するか、何をまだ決めないかを判断できる状態をつくることを中心価値とする。

## 3. 「設計Assessment」の意味

IT経営KAIZEN 設計Assessmentは、単なる現状調査・成熟度評価・IT健康診断ではない。

> **企業が目指す未来と現在の事実から、IT経営の次の一手を設計し、経営判断できる状態をつくるサービスである。**

ここでいう「設計」は、atLIBが完成した答えや特定製品を押し付けることを意味しない。

Futureを確認し、EvidenceからFACT / UNKNOWNを形成し、GapとRoot Causeを捉え、技術 × 運用 × 管理の構造と6つの改善視点からKAIZENの選択肢を整理する。そのうえで、経営が何を実行するか、何をやめるか、何を残すか、何を任せるか、何に投資するか、何を今は実施しないかをDecisionできる材料を形成する。

したがって、Assessmentの役割は「答えを決めること」ではなく、**良い経営Decisionができる状態を設計すること**にある。

短い価値表現候補：

> **事実から、IT経営の次の一手を設計する。**

これは現時点では商品説明・コピー候補であり、正式タグラインとしては確定しない。

## 4. 点数ではなくDecisionのためのAssessment

Assessmentは成熟度スコアや点数を中心に設計しない。

点数は、異なる意味を持つ状態を一つの数値へ圧縮し、経営者が「では何を決めればよいか」を判断する材料を失わせる可能性がある。

例えば「分からない」という状態にも、管理されていない、現場では管理されているが経営に報告されていない、報告されているが技術情報のままで経営が意味を理解できない、判断基準がない、現時点で本当に確認できない等の異なる状態がある。

これらを一つの「不明」「△」「0点」に潰さず、状態そのものを経営判断に必要な情報として扱う。

> **点数をつけるのではなく、現在地を事実で明らかにする。**
>
> **分からないことは、分からないまま正しく残す。**
>
> **その事実を、経営が判断できる情報に変える。**
>
> **そして、事実をもとにIT経営の次の一手を決める。**

## 5. FACT FIRSTと評価・提案の関係

FACT FIRSTは「FACT以外を書いてはいけない」という原則ではない。

> **FACT / UNKNOWN / Observation / Risk・Impact評価 / Hypothesis / Proposal / Decisionを混同しないことがFACT FIRSTである。**

確認されたFACTからFutureとのGapを捉え、そのGapによる経営上のRisk / Impactを評価し、Root Causeを仮説または確認済みの状態として整理し、KAIZEN Optionを提示することは可能である。

ただし、FACTから直接、根拠のない断定や特定施策へ飛躍してはならない。

基本構造：

> **FUTURE → FACT / UNKNOWN → GAP → RISK / IMPACT → ROOT CAUSE → KAIZEN OPTION → DECISION → ACT → CHANGE → NEW FACT**

Risk / Impact、Root Cause Hypothesis、KAIZEN Option等は、それぞれの状態・根拠を明示し、FACTそのものとして扱わない。

## 6. Assessmentの利用者と最終価値提供先

Assessmentは経営者本人だけが実施できるサービスではない。

執行役員、管理本部長、部長、情報システム責任者等がAssessmentの中心担当者となる場合も想定する。

> **Assessmentの利用者：経営者、または経営判断につなげる責任者**
>
> **最終的な価値提供先：経営**

担当責任者がEvidenceを集め、FACT / UNKNOWN / Gap / Root Cause / KAIZEN Optionを形成し、それを経営者へ説明してDecisionを求められる状態もAssessmentの重要な顧客体験とする。

Assessmentレポートは、Assessment参加者だけが理解できる報告書ではなく、**Assessment参加者が、その場にいなかった経営者へFACTに基づいて説明し、Decisionを求められる資料**として設計する。

これにより、IT部門・管理部門の課題や要望を、単なる部門要望ではなく、経営が判断できる事実と選択肢へ変換する。

価値表現候補：

> **IT部門の課題を、経営が判断できる言葉と事実に変える。**

これは現時点では価値表現候補であり、正式コピーとしては確定しない。

## 7. 顧客体験の基本方向

Assessmentでは、顧客が次の変化を体験できることを目指す。

> **未来を描く → 現在を事実で見る → 思い込みと事実を分ける → FutureとのGapを理解する → 次の一手を決める → 実行する → 本当に変わったかを確認する**

Assessment単体では主に「次の一手を決められる状態」までを形成し、その後のKAIZEN実行とFACTACTによってACT / CHANGE / NEW FACTを確認する。

Assessmentの終了条件は、単に報告書を納品したことや最終報告会を実施したことではなく、**経営が事実をもとに次の一手をDecisionできる状態が形成されていること**を原則とする。

## 8. AssessmentプロセスにおけるFACTACT

FACTACTはAssessment終了後に初めて利用する付加機能ではない。**Assessmentのプロセスそのものに介在する基盤**として扱う。

無料診断から引き継いだFuture、Respondent Statement、Observation、UNKNOWN、Hypothesis、Gap Candidate、Evidence Candidate等を起点に、Assessmentで確認するEvidenceとその確認結果をFACTACT上で整理・記録する。

Assessment中の基本的な流れは次のように考える。

> **Futureを確認する → 必要なEvidenceを確認する → FACT / UNKNOWNを形成する → Gapを捉える → Root Causeを整理する → KAIZEN候補を検討する → 人間が次の一手をDecisionする**

この過程でFACTACTは、少なくとも以下を支える。

- 情報の出所とEvidenceを保持する
- FACT / UNKNOWN / Observation / Hypothesis / Decision等を混同せず記録する
- 何を根拠に現在地を判断したかを残す
- Assessmentで形成した現在地を、その後のKAIZEN実行へ引き継ぐ
- Decisionの内容と、その根拠を記録する
- ACT / CHANGE / NEW FACTを同じ文脈で蓄積し、実際に会社が変わったかを確認できるようにする

したがってAssessmentの成果は、報告書だけではない。

> **Assessmentによって、企業のKAIZENの起点となる信頼できる現在地がFACTACT上に形成される。**

その現在地から、Decision、ACT、CHANGE、NEW FACT、NEXT KAIZENへ継続できることを顧客体験の一部として設計する。

ただし、FACTACTを使うこと自体を顧客価値にしない。FACTACTは、IT経営KAIZENの原則を一貫して実現し、Assessmentを一度きりの診断・報告書で終わらせないための基盤である。

## 9. 価値判断基準

Assessmentのプロセス、ヒアリング、Evidence確認、成果物、機能等を追加・削除する際は、次を判断基準とする。

> **これによって経営者は、事実をもとにIT経営の次の一手を決められるようになるか？**

この問いへの寄与が弱いものを、単に「コンサルティングらしい」「成果物として見栄えがする」「価格に見合う作業量を作る」といった理由だけで追加しない。

FACTACTの機能についても同様に、機能を使わせることを目的にせず、FACT FIRST、人間のDecision、CHANGE / NEW FACTの継続確認に必要かどうかで判断する。

## 10. 価格の扱い

Assessmentの商品設計が固まるまで、価格をサービス仕様の制約条件にしない。

設計後に、顧客が得る経営上の価値、顧客体験、必要なEvidence確認範囲、専門家の関与、実施期間、提供工数・原価、成果物、Assessment中にFACTACT上へ形成される現在地の価値、その後のKAIZEN実行・FACTACTとの継続接続価値を踏まえて適正価格を再評価する。

価格見直しの結果は80万円の維持、増額、減額のいずれもあり得る。価格ありきで結論を固定しない。

無料診断からAssessmentへの価値接続：

> **可能性で会社を変えない。事実を確認してから、何を変えるかを決める。**

Assessmentの提供価値：

> **事実をもとに、IT経営の次の一手を判断する材料を提供する。**

顧客の到達状態：

> **経営者が、事実をもとにIT経営の次の一手を決められる。**

IT経営KAIZEN全体へ展開可能な表現候補：

> **未来を描き、事実を知り、次の一手を決める。**

最後の表現は現時点ではコピー候補であり、正式なタグラインとしては確定しない。
