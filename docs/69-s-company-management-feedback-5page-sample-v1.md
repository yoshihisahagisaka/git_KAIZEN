# Page 1 — FUTURE

## Title

**1〜3年後、どんな会社にしたいか**

## Lead

IT経営KAIZENは、現在のIT課題からではなく、経営として実現したい会社のFUTUREから考えます。

## Current Customer Context — FACT

- 従業員200〜300名規模
- IPO準備中
- 情報システム部長が退職
- 情報システム部から情報システム課へ組織変更
- 新任の課長候補が着任
- 情報システム課は取締役本部長の所掌へ

## Main Question — 当日確認

> **IPOを一つの節目としたとき、1〜3年後、ITの面でもどんな会社になっていたいですか？**

現時点では未確認。

- ITに何を期待するか

- 経営から何が見えるようになっていてほしいか
- 新しい情報システム課に何を担ってほしいか
- IPOの先に実現したい会社の状態

## Footer Message

> **まずFUTUREを決める。現在地の評価は、そのFUTUREに対して行う。**

# Page 3 — GAP

## Title

**FUTUREとの間で、何を確認する必要があるか**

## Important Note

以下は現時点での**確認テーマ候補**です。FUTURE確認前にS社の課題として断定しません。

## 4 Candidate GAP Themes

### 01 MANAGEMENT / GOVERNANCE

**経営がITを判断できる状態か**

確認すること：
- ITの責任者 / Decision権限
- 投資・リスクの判断材料
- 経営へのReporting
- IPOを見据えたIT Governance

### 02 CONTINUITY

**人が変わってもITが継続できる状態か**

確認すること：
- 退職部長が持っていたKnowledge
- VendorとのRelation
- 過去Decisionとその理由
- 必要なEvidence / Documentation

### 03 OPERATION

**新任課長が本来担うべき仕事に時間を使える状態か**

確認すること：
- 定常業務のWork量
- 常駐者 / 新任課長 / Vendorの役割
- 標準化 / 自動化 / 委任可能性
- 改善・Managementへ使える時間

### 04 IPO / TRUST

**ITの状態を社内外へ説明できる状態か**

確認すること：
- IT統制
- Security
- Account / Asset管理
- Rule / Approval / Audit Evidence

## Footer Message

> **課題を決めつけるのではなく、FUTUREに対して確認すべきGAPを明らかにする。**

# Page 4 — WHY

## Title

**なぜ起きている可能性があるか**

## Label

**HYPOTHESIS — Evidence確認前の仮説**

### Hypothesis 1

IT運用とIT Managementの役割が明確に分かれていない可能性

**Observation**
- 常駐者はキッティング・問い合わせ・請求書管理等の定常業務を担当
- IT部長退職後、組織と所掌が変更

**Evidence Needed**
- 現行役割分担
- 責任 / 権限
- Decision Flow

### Hypothesis 2

Knowledge / Decision / Evidenceが特定の人に寄っていた可能性

**Observation**
- IT部長が退職
- 新任課長候補が着任

**Evidence Needed**
- 引継資料
- Vendor情報
- 過去Decision
- 運用Document / Evidence

### Hypothesis 3

定常業務と改善・経営Managementの仕事が競合する可能性

**Observation**
- 現在も日常的な定常業務が存在
- 新しい情報システム課体制へ移行

**Evidence Needed**
- Work量 / Human Work
- 新任課長の役割
- 社内外のCapability

### Hypothesis 4

IPOで必要なIT Capabilityと現在の体制との差がまだ可視化されていない可能性

**Observation**
- IPO準備中
- IT責任者 / 組織が移行期

**Evidence Needed**
- IPO準備上の要求
- 現行IT統制 / Security / Evidence
- 指摘事項の有無

## Footer Message

> **仮説のまま投資・体制を決めない。必要なEvidenceを確認する。**

# Page 5 — NEXT DECISION

## Title

**次に、何を決めるか**

## Lead

Management Feedbackのゴールは、atLIBのサービスを選ぶことではありません。

> **FUTUREを実現するために、次に何を確認し、何をDecisionする必要があるかを明確にすることです。**

## Candidate Management Decisions

### 01
**新しい情報システム課に、どのIT Capabilityが必要か**

### 02
**新任課長が担う仕事と、任せる仕事をどう分けるか**

### 03
**IPOを見据え、IT統制 / Security / Evidenceをどこまで確認・整備するか**

### 04
**現在のIT環境・運用・Vendorの何を残し、何を変えるか**

## Decision Route

### A — DIRECT ACT
必要な情報が十分で、そのまま実行をDecisionできる。

### B — FOCUSED CONFIRMATION
一部のEvidenceだけ追加確認する。

### C — DESIGN ASSESSMENT
経営Decisionに必要なEvidenceが不足しているため、事実を深く確認する。

### D — STOP / HOLD
現時点では進めない。

## Assessment Transition — Route C only

> **ここから先は、可能性のまま投資や体制を決めるのではなく、必要なEvidenceを確認して現在地と次の一手を確定する必要があります。**

> **そのための工程がIT経営KAIZENの設計Assessmentです。**

※ Assessmentの価格・Scopeは、Route CをHuman Decisionした後の正式提案で説明する。

## Final Question

> **今日の話を踏まえると、次に何を確認・判断する必要があると感じましたか？**

## Footer Message

> **何を変えるかを先に決める。誰が担うかは、その後に決める。**

# Customer-facing Language Rules

## Use

- 現時点で把握していること
- まだ確認が必要なこと
- 可能性
- 仮説
- Evidenceを確認する
- 次に何をDecisionするか

## Avoid before Evidence

- 問題です
- 原因です
- 必ず改善します
- IPOにはこれが必要です（個別要求を未確認のまま断定）
- S社にはAssessmentが必要です
- atLIBに任せるべきです
